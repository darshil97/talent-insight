## Deepgram authentication

The [temporary-token guide](https://developers.deepgram.com/guides/fundamentals/token-based-authentication) documents `POST https://api.deepgram.com/v1/auth/grant`, authenticated with the server's API key. The default token lifetime is 30 seconds; the key must have sufficient permissions. Voice Agent accepts these tokens. Token expiry restricts connection establishment, not the duration of an already open connection. Therefore a short token lifetime alone does not cap interview duration or spend.

The [Voice Agent reference](https://developers.deepgram.com/reference/voice-agent/voice-agent) documents `wss://agent.deepgram.com/v1/agent/converse`, settings messages, bearer authentication and browser authentication through WebSocket subprotocols. It exposes `ConversationText`, `SettingsApplied`, `UserStartedSpeaking`, `AgentAudioDone`, errors and function-call messages. Audio completion is not proof that an entire interview is complete. Design an explicit, idempotent application completion operation and distinguish normal completion, early termination and transport failure. Client-submitted transcripts are unverified candidate statements, not authenticated provider evidence.

## Browser SDK and dynamic configuration

The [browser JavaScript SDK](https://developers.deepgram.com/docs/browser-agent-javascript) provides `@deepgram/agents`, with session, microphone and playback primitives. Its documented `tokenFactory` obtains credentials at connect/reconnect time. It supports inline settings, so no separate dashboard agent per job is necessary. Documented transcript, speech-start, connection and error events support the proposed UI. Microphone permission and playback behavior still need real-browser verification.

The [React integration](https://developers.deepgram.com/docs/browser-agent-react) provides `@deepgram/react`, context and hooks for connection, transcript and audio controls. Evaluate it when module 13 begins; pin and verify the selected package then. Do not install it during initial setup solely for future voice work.

## Bedrock within Deepgram: module 12 decision (2026-10-27)

Rechecked on 2026-10-27 against the [LLM models guide](https://developers.deepgram.com/docs/voice-agent-llm-models), [reusable agent configurations](https://developers.deepgram.com/docs/reusable-agent-configurations), the [April 2026 changelog](https://developers.deepgram.com/changelog/2026/4/8), [token authentication](https://developers.deepgram.com/guides/fundamentals/token-based-authentication), [regional endpoints](https://developers.deepgram.com/reference/regional-endpoints) and [pricing](https://deepgram.com/pricing).

- **Native Bedrock:** `think.provider.type: aws_bedrock` takes only `credentials` of type `iam` or `sts` (access key, secret key, optional session token) inside `Settings`. There is no Bedrock API-key option. Because the browser sends `Settings`, every visitor could read those keys. Even per-session STS keys limited to one model would leave the interviewer instructions editable in the browser and require new IAM setup. The only latency saved would be the hop through FastAPI; the model's own response time dominates. Not used.
- **Reusable agent configurations** (April 2026): the `agent` block can be stored via the management API and referenced by UUID. Template variables (`DG_*`) are plain text, `is_sensitive` must be `false`, and the docs say not to store secrets. Variables are project-wide and visible to every project member, and configs are immutable. There is no dashboard support. A temporary token is not tied to a stored config, so a client can still send its own `Settings`. Not used.
- **Token grants:** `POST /v1/auth/grant` takes `ttl_seconds` (default 30, maximum 3600) and returns a JWT with `usage:write` for `/listen`, `/speak`, `/read` and the `/agent` WebSocket. Management APIs are excluded. The token must be valid only when the connection opens, so it does not limit session length.
- **Custom LLM:** `provider.type: open_ai` with `endpoint.url` and optional `endpoint.headers`, in the OpenAI Chat Completions format. The streaming contract, function forwarding and whether `think.prompt` is forwarded are not documented. `context_length` applies only to custom endpoints, and `mip_opt_out` exists.
- **Regions:** agent endpoints are general (`agent.deepgram.com`), EU, AU (`api.au.deepgram.com`) and India (`api.in.deepgram.com`). The selected Bedrock model runs in Sydney.
- **Pricing** (pay-as-you-go, billed by connection time):
  - Standard managed LLM: $0.075/min.
  - Advanced managed LLM: $0.163/min.
  - BYO LLM: $0.065/min.
  - New accounts get $200 of credit.
  - Third-party price lists give Bedrock `gpt-oss-120b` at about $0.15 / $0.60 per million input/output tokens (AWS's own page not confirmed). That makes a 10-minute FastAPI-interviewer screening about $0.67, against about $0.75 on a managed Standard model.

**Decision, by the user after review:** a narrowly scoped FastAPI interviewer endpoint calls Bedrock server-side, and Deepgram calls it as a custom LLM, with audio staying browser ↔ Deepgram. See [voice sessions](voice-sessions.md). This keeps AWS keys and the interviewer's instructions on the server, and lets the server enforce the time box and see each turn. The costs are an extra text hop, a public HTTPS backend, and a per-session capability that the browser can see; that capability is bounded by turns, size and expiry. Still unverified: Deepgram's streaming and function behavior against a custom endpoint, and Deepgram and AWS retention. A managed LLM or proxied audio was not adopted.

Live checks on 2026-10-28, one each, approved by the user:
- **Deepgram grant:** a real `auth/grant` call returned a 30-second JWT in about 1.0 s. Its scope claim is `asr:write`, not the documented `usage:write`, and whether the Voice Agent socket accepts it is not yet verified.
- **Interviewer turn:** one synthetic turn on `gpt-oss-120b` in Sydney, at low reasoning effort, produced its first text after 4.6 s and finished at 4.7 s, measured from India. That is too slow for natural voice. A faster interviewer model needs to be evaluated.
- **Interviewer model comparison:** after the separate interviewer setting was added, three scripted turns per model were run. Claude Haiku 4.5 through the `au.` profile handled declined topics and endings best, with about 1 s to first text when warm. Nova Lite was fastest at about 0.7 s and also behaved correctly. Ministral 3 14B was correct but returned whole replies at once. `gpt-oss-20b` repeated a declined question, and `gpt-oss-120b` packed several questions into one reply and ended early. Claude Haiku 5.5 is listed but returns `AccessDeniedException` for this account. See [voice sessions](voice-sessions.md#interviewer-model-comparison-2026-10-28-user-approved). See [voice sessions](voice-sessions.md#live-checks-2026-10-28-user-approved).

## Backend Bedrock integration

[AWS Converse documentation](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html) describes a common model interface and the required inference permissions. [LangChain's Bedrock integration](https://docs.langchain.com/oss/python/integrations/chat/bedrock) recommends `ChatBedrockConverse` for supported use cases; use `langchain-aws` with the normal AWS credential chain behind a small backend adapter.

[AWS structured-output documentation](https://docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html) describes schema-constrained Converse output and strict tool use, with model/profile and schema-subset restrictions. Confirm compatibility of the account, region, selected model or inference profile and pinned SDK. Always apply Pydantic validation and evidence checks, even when native schema enforcement is available. If unsupported, use a documented validated tool-output path or return a clear capability error; never accept arbitrary JSON unchecked.

Module 9 user selection: `openai.gpt-oss-120b-1:0` in `ap-southeast-2` (Sydney), using the user-provided `AWS_BEARER_TOKEN_BEDROCK` from the ignored backend dotenv. The [AWS model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-openai-gpt-oss-120b.html) documents this model's Converse endpoint and in-region Sydney availability. Documentation alone did not establish account access; bounded synthetic calls then confirmed the key could invoke the model. No IAM permissions or infrastructure were changed. [AWS's API-key guide](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html) documents bearer-key authentication; the pinned `boto3==1.43.118`, `botocore==1.43.118` and `langchain-aws==1.9.0` support it.

Actual module 9 checks: six small synthetic-only Converse calls, each capped at 2,048 output tokens with one SDK attempt and no service retry. Three explored native JSON requests: the first two outputs failed local validation; the final request included the exact schema in the system prompt as well as `outputConfig`, and returned two facts that passed Pydantic and exact source-quote verification. Three tool-output checks returned no accepted structured tool result. This does not establish a success rate, an accuracy score or provider-enforced schema guarantees. No real resume or transcript was sent. Raw responses/reasoning, source content and credentials were not written into application files or routine logs.

The saved method is explicitly `BEDROCK_STRUCTURED_METHOD=json_schema`, with the full schema also stated in the server prompt. Do not automatically fall back between JSON, tool or mock paths. Native output configuration is not a reason to skip local validation. The parser independently rejects incomplete/fenced JSON that a generic JSON parser might repair; schema, quotes, phrase provenance and page ranges are checked again before returning facts. The selected model's reasoning blocks are discarded. [AWS tool-use documentation](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use-client-side.html) distinguishes automatic tool selection from model-specific forced choices; a tool method must be verified for the actual selected model/profile before use.

On 2026-10-26 the user's first 13-membership synthetic refresh stopped on `invalid_model_output`. Bounded diagnostics reproduced a model response that ended normally but added a redundant opening brace before the required `facts` root. LangChain's generic parser repaired it; the application rejected the raw malformed JSON. The worker now normalizes only that observed root-brace error, then parses complete JSON and revalidates schema, exact quotes and source offsets. It never accepts generic incomplete/fenced JSON or uses a provider-supplied score. A subsequent full refresh completed all 13 memberships and the backend independently revalidated source citations and deterministic scoring. This establishes that this batch completed, not a general success rate or semantic matching accuracy. No private resume, raw model response, reasoning block or credential was saved in application files or routine logs.

A later, explicitly authorized diagnostic of one uploaded PDF for the Backend Engineer role reproduced `invalid_model_output`. At the former 3,000-token output cap, one response reached `max_tokens`; another ended normally but failed exact evidence validation. Raising the cap to 8,192 exposed a separate limit: a complete response contained more than the local maximum of 40 facts. A prompt requesting at most 12 job-focused facts reduced that response to eight facts, but one value still exceeded the 200-character local limit. The prompt now requests short literal values while retaining the original hard limits and quote checks. One approved full assessment with this prompt succeeded: eight verified facts and six requirement judgments, three unknown. The point score remained unavailable as designed. Diagnostics reported only safe error categories and counts, without storing resume or response text. Each finding comes from a bounded run, so none establishes a general model success rate or semantic accuracy.

Regenerating the thirteen synthetic snapshots with the revised worker encountered intermittent `invalid_model_output` and `provider_timeout` failures on different candidates. The refresh now checkpoints only validated synthetic extractions and completed assessments in ignored local files. It resumes matching entries after a failure and publishes the complete snapshot atomically. A later approved run completed all thirteen, and local checks revalidated their citations and deterministic scores. The checkpoint reduces repeated provider work; it does not make the model reliable or weaken validation.

After the user reported that Bedrock sometimes responds slowly, the local SDK read timeout was increased from 20 to 60 seconds and the per-stage deadline from 45 to 130 seconds. Offline adapter tests confirm the configured bounds. No live slow-response call was made after this change, so its effect on provider failures is not yet verified. The existing 13 synthetic results were preserved by an offline fingerprint rebind after checking the exact prior worker bytes, fixture identity, stored digests, citations and recomputed scores; their model judgments were not regenerated.

On 2026-10-27 the backend AI path was refactored (Jinja prompts, a provider registry, in-process cached Bedrock client, per-item salvage, tolerant JSON capture and retry hints). The earlier failures above motivated the changes: whitespace/ligature differences now map to exact source spans instead of failing, unverifiable facts or judgments are discarded or set to unknown instead of failing the whole request, and wrapped or fenced complete JSON is captured. Partial JSON, truncated responses and unverified quotes are still rejected. Temperature is now sent explicitly (default 0); `reasoning_effort` is configurable but unset. The approved live refresh after the refactor stopped at its first call with AWS `AccessDeniedException` (`provider_access_denied`). An offline check with a synthetic token confirmed the new client sends `Authorization: Bearer` to the `ap-southeast-2` Converse endpoint, as the previous worker did, and the user's `check_bedrock.py` isolated the cause: a stale `AWS_BEARER_TOKEN_BEDROCK` exported in this machine's shell profile overrides `backend/.env`, because process variables take precedence. With only that variable removed, a minimal call using the `backend/.env` key succeeded. Remove or update stale shell exports before running backend Bedrock commands. At the user's request the refresh was then run with `env -u AWS_BEARER_TOKEN_BEDROCK` so the `backend/.env` key applied. All 13 memberships succeeded: 26 Bedrock calls, each accepted on its first attempt with `end_turn`, with no retries, discarded facts or forced-unknown judgments; calls took about 3–10 seconds and used 37,042 input and 28,336 output tokens in total. The new snapshot has four point scores and nine ranges, with 23 unknown requirement judgments (the previous snapshot had five point scores and eight ranges); Backend Engineer Theo in the Data Scientist pool keeps an 18.3–66.7 range with no point score. Offline revalidation passed for all 13 entries (fingerprint and digest, exact quote spans, deterministic score recomputation), checkpoints were removed, and the backend suite passed 312 tests with three opt-in Neon checks skipped. One clean batch is not a success rate or an accuracy evaluation; the interpretations still need human review. That rerun supplied the first live calls with the refactored prompts and temperature setting; it exercised no salvage or retry path because every response verified.

A second run on 2026-10-27 compared CAS-style sectioned prompts against that run. The sectioned prompts kept every call on its first attempt but discarded 7 unverifiable facts (version 1 discarded none), changed 13 of 78 judgments, and used about 25% more input tokens. They judged two 'not stated' lines as `not_met`, which treats missing evidence as contrary evidence, and lost one candidate's verified experience fact. Version 1 had the opposite error on another candidate. With one run each, these differences may partly be run-to-run variation; see `PROJECT_CONTEXT.md` for the full counts. A third run added an explicit rule that statements of missing information are `unknown`: it discarded no facts, cut `not_met` from 10 to 4 and left no resolved judgment resting only on a 'not stated' fact, but judged two 'training or equivalent practical experience' requirements `unknown` despite relevant experience. Module 11a then added the `transferable` level, applied-use rules and identity extraction; across two further runs the model used `transferable` once (adjacent HR experience) and still judged verified Go backend experience `unknown` for a Python services requirement despite an explicit example, so model-only transferable judgments remain inconsistent. Name and title extraction matched all 13 synthetic fixtures.

LangSmith is a transitive dependency of the chosen adapter, but tracing flags are forced off whenever a Bedrock client is built and its pytest plugin is disabled in project test options. No prompt cache is requested. AWS invocation-logging/retention settings and real-document privacy remain unverified; application non-persistence does not establish those policies. ## Neon Postgres

Neon's [SQLAlchemy guide](https://neon.com/docs/guides/sqlalchemy) documents standard PostgreSQL connectivity. Its [pooling guide](https://neon.com/docs/connect/connection-pooling) describes PgBouncer transaction pooling and related session-state constraints. Recommend SQLAlchemy 2 with psycopg, a bounded application pool and TLS. Use a direct connection for Alembic migrations to avoid session-state surprises; configure runtime and migration URLs separately.

The existing `talent-insight` project, its single `production` branch and `neondb` database were inspected and initialized with the approved catalog migration and synthetic seed. Pooled runtime and direct migration connectivity, schema parity, evidence and repeatable seeding are verified on Neon PostgreSQL 18.6. Local and hosted backend runs share this Neon database; no local PostgreSQL server is used. Default checks need no database; opt-in integration tests use read-only transactions. See [database setup](database.md) for the exact target and commands. Object storage remains optional and unused.

## Public-demo boundary

CORS controls cooperating browsers; it does not authenticate API callers or enforce provider cost limits. Before public voice access, verify token scope, server-enforceable session duration, concurrency and project spend limits. A browser can change settings and ignore a client-side stop timer. A single-process in-memory limiter is only a development safeguard, not a distributed budget control.

Signed temporary candidate context can detect modification but is readable by its holder. Keep it short-lived, size-limited and out of URLs/logs; do not put resumes in an opaque-looking token and assume confidentiality. Session design remains pending, including replay/duplicate protection, expiry and cleanup. Backend transcript validation can check structure and consistency but cannot prove a browser transcript authentic.
